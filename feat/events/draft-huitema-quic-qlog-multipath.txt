        QLOG extensions for Multiple Paths for a QUIC Connection
                draft-huitema-quic-qlog-multipath-latest

Abstract

   This draft define the QLOG elements that have to be added to the
   definition of QLOG events for QUIC connections.

1.  Introduction

   The QLOG drafts define the syntax of QLOG
   [I-D.ietf-quic-qlog-main-schema] and the events and frames for
   logging QUIC events [I-D.ietf-quic-qlog-quic-events] found in QUIC
   connections per [RFC9000].  The extensions to [RFC9000] for managing
   multiple paths for a QUIC connections are defined in [RFC10069],
   which introduces new concepts such as path, new events such as
   creating or abandoning paths, and new frames for managing traffic
   when using multiple paths.  This draft defines the corresponding QLOG
   extensions.

3.  Event Schema Definition

   This document extends the quic namespace of
   [I-D.ietf-quic-qlog-quic-events] to cover the multipath extension
   defined in [RFC10069].  The event schema URI is
   urn:ietf:params:qlog:events:quic#multipath, following Section 8.1 of
   [I-D.ietf-quic-qlog-main-schema].

3.1.  Draft Event Schema Identification

   This section is to be removed before publishing as an RFC.

   Only implementations of the final, published RFC can use the events
   belonging to the event schema with the URI
   urn:ietf:params:qlog:events:quic#multipath.  Until such an RFC
   exists, implementations MUST NOT identify themselves using this URI.

   Implementations of draft versions of the event schema MUST append the
   string "-" and the corresponding draft number to the URI.  For
   example, draft 00 of this document is identified using the URI
   urn:ietf:params:qlog:events:quic#multipath-00.

4.  Multipath specific events and event extensions

   The three events in this section have Base importance.  They record
   changes to the paths of a connection as seen by the endpoint.  Packet
   events record the frames that carry path management signals.  A
   single change can involve several frames, and a local decision can
   precede the first frame that signals it.

   Each of these events MUST identify the affected path using a top-
   level path_id field of type uint32 alongside time, name, and data
   (Section 7 of [I-D.ietf-quic-qlog-main-schema]).  Its value is the
   Path ID from [RFC10069], scoped to the connection.  For example, if a
   packet on path 0 changes the status of path 1, the status event has
   path_id 1.  The optional qlog tuple field identifies the network
   tuple associated with an event.  Two Path IDs can share a tuple, and
   a path can change tuples during migration.  Tuple details can be
   recorded with quic:tuple_assigned ([I-D.ietf-quic-qlog-quic-events]).

   The event data types extend the qlog main schema as follows.  Fields
   of type QUICPathVarInt hold the decoded value of a QUIC variable-
   length integer and follow the qlog serialization rules for uint64.

   $ProtocolEventData /= QUICPathCreated / QUICPathAbandoned /
                         QUICPathStatusUpdated

   QUICPathVarInt = 0..4611686018427387903  ; 2^62 - 1

4.1.  path_created

   quic:path_created is emitted once when the endpoint starts using a
   Path ID for a new path.  For an additional path, the client logs the
   event when it initiates the path and the server logs it when it
   accepts the attempt and sets up the path locally (Section 3.1 of
   [RFC10069]).  Validation can still be pending.  For the initial path,
   the endpoint logs the event with path_id 0 when the handshake
   completes with multipath negotiated.  Issuing connection IDs for
   future paths alone does not trigger this event.  Migration to a new
   tuple retains the existing Path ID and can be logged with
   quic:migration_state_updated.

   QUICPathCreated = {
       * $$quic-pathcreated-extension
   }

4.2.  path_abandoned

   quic:path_abandoned is emitted once when the endpoint abandons the
   indicated Path ID under Section 3.4 of [RFC10069].  The initiator is
   local when the endpoint decides to close the path and remote when it
   acts on the peer's PATH_ABANDON.  These values use the Initiator type
   from [I-D.ietf-quic-qlog-quic-events].  If known, error_code records
   the numeric PATH_ABANDON error code for that decision.

   An unused Path ID can be abandoned without a preceding path_created.
   A repeated or reciprocal PATH_ABANDON and the eventual release of
   retained path state do not produce additional abandonment events.

   QUICPathAbandoned = {
       initiator: Initiator
       ? error_code: QUICPathVarInt
       * $$quic-pathabandoned-extension
   }

4.3.  path_status_updated

   quic:path_status_updated is emitted when the endpoint changes the
   path usage preference it advertises (initiator is local), or records
   a change in the peer's advertised preference (initiator is remote).
   Each endpoint expresses its own preference for how its peer should
   use the path (Section 3.3 of [RFC10069]).  A sender can choose how to
   schedule packets independently of the advertised preference.

   new gives the updated preference.  If included, old gives the
   previous preference for the same Path ID and initiator.  Omit old
   when no previous preference is known.  The first advertisement can
   precede path creation. sequence_number, if present, is the Path
   Status Sequence Number of the advertisement.  An ignored out-of-order
   or duplicate advertisement, or a newer advertisement that repeats the
   current preference, produces no status change event (Section 4.3 of
   [RFC10069]).

   QUICPathStatusUpdated = {
       initiator: Initiator
       ? old: QUICPathStatus
       new: QUICPathStatus
       ? sequence_number: QUICPathVarInt
       * $$quic-pathstatusupdated-extension
   }

   QUICPathStatus = "available" / "backup"

4.4.  Example

   In this excerpt from a client's event list, the client opens path 1.
   It then receives the peer's first preference for path 1 in a packet
   on path 0.  Later the client abandons path 1 at the application's
   request.

   [
     { "time": 12.0, "name": "quic:path_created",
       "path_id": 1, "data": {} },
     { "time": 18.0, "name": "quic:path_status_updated",
       "path_id": 1, "data": { "initiator": "remote", "new": "backup",
                               "sequence_number": 0 } },
     { "time": 97.0, "name": "quic:path_abandoned",
       "path_id": 1, "data": { "initiator": "local", "error_code": 62 } }
   ]
