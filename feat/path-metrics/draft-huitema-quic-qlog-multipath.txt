Abstract

   This draft define the QLOG elements that have to be added to the
   definition of QLOG events for QUIC connections.

1.  Introduction

   The QLOG drafts define the syntax of QLOG
   [I-D.ietf-quic-qlog-main-schema] and the events and frames for
   logging QUIC events [I-D.ietf-quic-qlog-quic-events] found in QUIC
   connections per [RFC9000].  The extensions to [RFC9000] for managing
   multiple paths for a QUIC connections are defined in [RFC10069],
   which introduces new concepts such as path, new events such as
   creating or abandoning paths, and new frames for managing traffic
   when using multiple paths.  This draft defines the corresponding QLOG
   extensions.

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",

3.  Event Schema Definition

   This document describes how the extend extensions to the core QUIC
   protocol defined in [RFC10069] can be expressed by extending the
   schema defined in [I-D.ietf-quic-qlog-quic-events].  Per the
   requirements in Section 8 of [I-D.ietf-quic-qlog-main-schema], this
   document registers extensions to the quic namespace.  The event
   schema URI is: urn:ietf:params:qlog:events:quic-multipath.

3.1.  Draft Event Schema Identification

   This section is to be removed before publishing as an RFC.

   Only implementations of the final, published RFC can use the events

5.  Multipath specific frames

   The following CDDL extends the $QuicFrame type socket defined in
   Section 8.13 of [I-D.ietf-quic-qlog-quic-events].  These frame
   objects can appear wherever a QUIC event records frames, including
   the frames array of quic:packet_sent and quic:packet_received.  The
   optional raw field uses RawInfo from
   [I-D.ietf-quic-qlog-main-schema].

   Within a frame, path_id is the Path Identifier carried on the wire.
   For example, a PATH_ACK sent on path 0 can acknowledge packets on
   path 1.  In that case the PATH_ACK object contains "path_id": 1.
   Path IDs and path ID limits are unsigned 32-bit values.  QUIC
   variable-length integer fields are logged as decoded values within
   the limits of [RFC10069].

   $QuicFrame /= PathAckFrame / PathAbandonFrame / PathStatusFrame /
                 PathNewConnectionIDFrame / PathRetireConnectionIDFrame /
                 MaxPathIDFrame / PathsBlockedFrame / PathCIDsBlockedFrame

5.1.  PATH_ACK

   Both wire types in Section 4.1 of [RFC10069] use the frame type
   path_ack.  The path_id selects the packet number space being
   acknowledged.  As in the base AckFrame, ack_delay is expressed in
   milliseconds after applying the ACK delay exponent.  The acked_ranges
   field contains decoded, inclusive packet number ranges.  For example,
   [[40, 42], [48]] acknowledges packets 40 through 42 and packet 48.

   For wire type 0x3e, omit the ECN counts.  For 0x3f, include all three
   cumulative counts for the acknowledged path, including counts of
   zero.

   PathAckFrame = { PathAckFields } /
                  { PathAckFields, ect0: uint64, ect1: uint64, ce: uint64 }

   PathAckFields = (
       frame_type: "path_ack"
       path_id: uint32
       ? ack_delay: float32
       ? acked_ranges: [+ AckRange]
       ? raw: RawInfo
   )

5.2.  PATH_ABANDON

   For PATH_ABANDON (0x3e75), path_id identifies the path being closed.
   The error field uses qlog transport error names, including no_error
   for code 0.  The four additional names below correspond to the codes
   in Section 4.2.1 of [RFC10069].  For a code with no known name, log
   "error": "unknown" and include its numeric value in error_code.

   PathAbandonFrame = {
       frame_type: "path_abandon"
       path_id: uint32
       error: $TransportError / CryptoError
       ? error_code: uint64
       ? raw: RawInfo
   }

   $TransportError /= "application_abandon_path" /      ; 0x3e
                      "path_resource_limit_reached" /   ; 0x3e75
                      "path_unstable_or_poor" /         ; 0x3e76
                      "no_cid_available_for_path"       ; 0x3e77

5.3.  PATH_STATUS_AVAILABLE and PATH_STATUS_BACKUP

   The frame_type identifies the preference advertised for path_id.  Use
   path_status_available for 0x3e77 and path_status_backup for 0x3e76.
   Both use the same per-path status sequence number space (Section 4.3
   of [RFC10069]).  The frame object records the received sequence
   number even when the receiver ignores an outdated advertisement.

   PathStatusFrame = {
       frame_type: "path_status_available" / "path_status_backup"
       path_id: uint32
       sequence_number: uint64
       ? raw: RawInfo
   }

5.4.  PATH_NEW_CONNECTION_ID and PATH_RETIRE_CONNECTION_ID

   These frames use the fields of the base NewConnectionIDFrame and
   RetireConnectionIDFrame, with an additional path_id.  Both the
   connection ID sequence number and the retirement threshold apply to
   the indicated path (Sections 4.4 and 4.5 of [RFC10069]).  For
   PATH_NEW_CONNECTION_ID (0x3e78), connection_id_length, when present,
   is the length in bytes of the connection ID on the wire.  For
   PATH_RETIRE_CONNECTION_ID (0x3e79), the pair (path_id,
   sequence_number) identifies the connection ID to retire.

   PathNewConnectionIDFrame = {
       frame_type: "path_new_connection_id"
       path_id: uint32
       sequence_number: uint64
       retire_prior_to: uint64
       ? connection_id_length: uint8
       connection_id: ConnectionID
       ? stateless_reset_token: StatelessResetToken
       ? raw: RawInfo
   }

   PathRetireConnectionIDFrame = {
       frame_type: "path_retire_connection_id"
       path_id: uint32
       sequence_number: uint64
       ? raw: RawInfo
   }

5.5.  MAX_PATH_ID, PATHS_BLOCKED, and PATH_CIDS_BLOCKED

   MAX_PATH_ID (0x3e7a) advertises the largest acceptable Path ID in
   maximum.  PATHS_BLOCKED (0x3e7b) reports the Path ID limit in effect
   at the sender in limit.  Both fields represent the Maximum Path
   Identifier on the wire.  PATH_CIDS_BLOCKED (0x3e7c) identifies the
   path that lacks an unused connection ID and reports the next
   connection ID sequence number expected from the peer (Sections 4.6
   and 4.7 of [RFC10069]).

   MaxPathIDFrame = {
       frame_type: "max_path_id"
       maximum: uint32
       ? raw: RawInfo
   }

   PathsBlockedFrame = {
       frame_type: "paths_blocked"
       limit: uint32
       ? raw: RawInfo
   }

   PathCIDsBlockedFrame = {
       frame_type: "path_cids_blocked"
       path_id: uint32
       next_sequence_number: uint64
       ? raw: RawInfo
   }

5.6.  Example

   In this packet sent on path 0, the PATH_ACK acknowledges packets on
   path 1 and the PATH_CIDS_BLOCKED reports that the sender has run out
   of connection IDs for path 2.

   {
     "time": 16.5,
     "name": "quic:packet_sent",
     "path_id": 0,
     "data": {
       "header": { "packet_type": "1RTT", "packet_number": 90 },
       "frames": [
         { "frame_type": "path_ack", "path_id": 1,
           "acked_ranges": [[40, 42], [48]],
           "ect0": 4, "ect1": 0, "ce": 0 },
         { "frame_type": "path_cids_blocked", "path_id": 2,
           "next_sequence_number": 3 }
       ]
     }
   }

6.  Per-path congestion control and recovery

   Each path has its own Application Data packet number space and
   congestion control state (Sections 1 and 5.3 of [RFC10069]).  The
   following events reuse the names and data fields in
   [I-D.ietf-quic-qlog-quic-events].  For an event attributable to one
   known path, include its unsigned 32-bit path_id alongside time, name,
   and data.  Path 0 is identified explicitly.  Omit path_id for
   connection-wide events or when the path is unknown.

6.1.  Congestion control and RTT

   In quic:recovery_metrics_updated, path_id identifies the path whose
   metrics changed.  For example, an update can group congestion_window,
   bytes_in_flight, ssthresh, and pacing_rate for one path.  In a path-
   scoped update, packets_in_flight counts packets across the packet
   number spaces of that path.  Emit separate updates for different
   paths and for any connection-wide values, including shared controller
   state.  The same scope applies to quic:recovery_parameters_set and
   quic:congestion_state_updated.

   When a PATH_ACK updates latest_rtt, smoothed_rtt, or another RTT
   metric, path_id identifies the path whose estimator was updated.  The
   sample can include the return delay on another path (Section 5.4 of
   [RFC10069]).  For example, if a PATH_ACK arrives on path 0 for
   packets sent on path 1, quic:packet_received reports path 0.  The
   PATH_ACK frame and quic:packets_acked identify path 1.  Group
   acknowledged packet numbers by path and packet number space.

6.2.  Probe timeout, packet loss, and retransmission

   For a per-path probe timeout (PTO), quic:timer_updated identifies the
   path whose timer was set, expired, or was cancelled.  A PTO
   expiration uses timer_type of "pto" and event_type of "expired".  An
   implementation that logs a combined loss detection timer can use
   "loss_timeout" and include path_id when the update concerns one known
   path.  The current pto_count can be recorded in
   quic:recovery_metrics_updated.  A probe transmission uses
   quic:packet_sent with trigger "pto_probe" on the path carrying the
   probe.  PTO expiration alone does not establish packet loss
   (Section 5.7 of [RFC10069]).

   In quic:packet_lost, path_id identifies the original sending path.
   Together with the sending endpoint, packet number space, and packet
   number, it identifies the packet declared lost.  The base trigger
   values "reordering_threshold" and "time_threshold" apply per path.
   An endpoint that discards the state of an abandoned path also
   declares its outstanding packets lost (Section 3.4.3 of [RFC10069]).
   For packets first declared lost for this reason, the endpoint SHOULD
   include path_state_discarded in the event data and omit trigger.  The
   field is absent for other loss declarations.

   $$quic-packetlost-extension //= (
       ? path_state_discarded: true
   )

   In quic:marked_for_retransmit, path_id identifies the original
   sending path of the data marked after loss detection.  Group data
   from different known source paths in separate events.  The later
   quic:packet_sent identifies the path selected for the new packet.
   STREAM data can be split or combined when sent again.  When frame
   details are logged, the stream ID and overlapping byte ranges
   identify repeated data across paths (Section 5.6 of [RFC10069]).

6.3.  Example of cross-path recovery

   In this sender trace excerpt, a PTO on path 1 prompts a probe.  A
   PATH_ACK arriving on path 0 acknowledges the probe on path 1.  The
   sender then declares packet 42 on path 1 lost by the packet threshold
   and resends its stream bytes on path 0.  The new packet also has
   number 42 in its own packet number space.

   [
     { "time": 0, "name": "quic:packet_sent", "path_id": 1,
       "data": {
         "header": { "packet_type": "1RTT", "packet_number": 42 },
         "frames": [{ "frame_type": "stream", "stream_id": 0,
                      "offset": 800, "raw": { "length": 800 } }] } },
     { "time": 160, "name": "quic:timer_updated", "path_id": 1,
       "data": { "timer_type": "pto", "event_type": "expired",
                 "packet_number_space": "application_data" } },
     { "time": 160, "name": "quic:packet_sent", "path_id": 1,
       "data": {
         "header": { "packet_type": "1RTT", "packet_number": 45 },
         "trigger": "pto_probe",
         "frames": [{ "frame_type": "ping" }] } },
     { "time": 186, "name": "quic:packet_received", "path_id": 0,
       "data": {
         "header": { "packet_type": "1RTT", "packet_number": 9 },
         "frames": [{ "frame_type": "path_ack", "path_id": 1,
                      "acked_ranges": [[45]] }] } },
     { "time": 186, "name": "quic:packet_lost", "path_id": 1,
       "data": {
         "header": { "packet_type": "1RTT", "packet_number": 42 },
         "trigger": "reordering_threshold" } },
     { "time": 186, "name": "quic:recovery_metrics_updated",
       "path_id": 1,
       "data": { "congestion_window": 6000, "pto_count": 0 } },
     { "time": 186, "name": "quic:marked_for_retransmit", "path_id": 1,
       "data": { "frames": [{ "frame_type": "stream", "stream_id": 0,
                    "offset": 800, "raw": { "length": 800 } }] } },
     { "time": 187, "name": "quic:packet_sent", "path_id": 0,
       "data": {
         "header": { "packet_type": "1RTT", "packet_number": 42 },
         "trigger": "retransmit_reordered",
         "frames": [{ "frame_type": "stream", "stream_id": 0,
                      "offset": 800, "raw": { "length": 800 } }] } }
   ]
